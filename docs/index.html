SCENARIOS

What it manages, and who it is for

From a single listening room to a multi-terminal Hi-Fi fleet — Zephyr HiFi Kit converges Roon / HQPlayer playback terminals, x86 mini PCs, and Raspberry Pi ARM terminals onto one Linux or Windows server, with unified orchestration, signed delivery, and staged rollouts. These are the situations it is built for.

Multi-terminal Hi-Fi fleets

One server runs many playback terminals, and Roon Bridge, HQPlayer NAA, and system updates share a single GPG-signed delivery chain: define the desired state once and the whole fleet converges.

01 · CAPABILITIES

Nine domains, all really implemented

Not a roadmap, not placeholders. Every item below has corresponding Go code, API routes, and end-to-end smoke assertions in the repository.

Delivery core

An application catalog and multi-arch artifact repository, with GPG verification enforced on ingest. BOM desired state supports draft, validate, publish, import, export, and rollback to history; the job state machine runs from preflight to verification, with automatic rollback on failure.

  • Ingest enforces signature verification; unsigned artifacts are rejected
  • Full BOM version history, rollback to any published version
  • Playback gating: never interrupt playback, services wait for idle
  • 10-stage job state machine with a failure rollback chain

Terminal lifecycle

One-time registration tokens (TTL optional), a three-step add wizard, terminal configuration panels, and restore after deregistration.

  • Alias · room · desired BOM · DAC arbitration
  • Playback protection · maintenance windows · offline threshold
  • Deregister with undo, so mistakes are reversible

Licensing

Offline-signed license activation, real-time seat usage, and per-terminal grant and revoke.

  • Licenses are signed offline; the server only verifies
  • License and authorization gates before every rollout
  • Seat usage at a glance; overage is blocked immediately

Operations and diagnostics

Remote apt checks and upgrades over a dedicated command channel; mDNS / SSDP / multicast network diagnostics; alerts for a kernel awaiting reboot.

  • Rollouts advance ring by ring; no progress while a ring is incomplete
  • System upgrades gated by playback protection on both sides
  • Network diagnostics pinpoint discovery protocol faults

Trust root

An offline master key, controlled signing subkeys, and a server-side public-key trust root split the work; keys can be imported and trust roots exported.

  • The server never holds a private key
  • Terminal local console changes require the node key
  • Operation log with CSV / JSON export

Music and terminal center

Start listening from the home page, with a site-wide player bar available on every page; a categorized library and favorites make picking tracks easy, and the terminal center manages playback devices in one place.

  • Home page and site-wide player bar
  • Categorized library and favorites
  • Add and manage terminals in the terminal center

Terminal agent

Registration, heartbeat, snapshots; job execution covers apt, dpkg, config rendering, and a systemd unit allowlist; DAC arbitration and local playback protection gates; a built-in local console (services, system updates, network diagnostics, power). It runs as root, but every action is bound by the allowlist and switches.

Audio stack · the ZAT protocol

Not just orchestrating someone else's playback terminals — Zephyr HiFi Kit is a complete audio path in its own right: the kernel mounts SMB/CIFS libraries, formats such as WAV / FLAC are identified by file header, the server decodes with libFLAC, and audio is streamed to terminals over its own ZAT protocol (sample-clock PTS, node-key authentication, license gating) for bit-perfect ALSA output. The terminal's Now Playing console supports pause, stop, seek, volume, and output device switching, and is wired into playback gating. Real output needs the audio build (CGO); ALSA is a placeholder in the management build.

  • SMB/CIFS kernel mounts plus library scan and ingest, credentials never on the command line
  • WAV / FLAC format detection with real libFLAC decoding
  • ZAT streaming: sample-clock PTS · node-key authentication · license gating
  • Bit-perfect ALSA output plus the Now Playing console on the terminal

Auto-update · server self-upgrade and terminal convergence

The server periodically checks the release source for the latest version, verifies it three ways (feed SHA256 digest, optional GPG signature, and the in-package SHA256SUMS), then atomically swaps the binary and restarts while refreshing the terminal distribution set. Terminal agents always follow the server: signed upgrade commands go out ring by ring, and download, verification, dpkg, and restart are fully automatic; convergence is confirmed only after the heartbeat reports the new version. Failures back off and retry, and once the limit is reached they are suspended with one-click retry, while playing terminals wait for idle on their own. On an offline network, point the release source at a mirror and the loop closes.

  • Triple verification plus atomic swap; a crash never leaves a half-written binary
  • Rings advance only when fully aligned; parallelism and retry limits are adjustable
  • Playback protection gates both sides, so upgrades never cut the sound
  • Live console state: check · upgrade · converge · retry suspended

02 · ARCHITECTURE

The signing chain decides who can deliver

Artifacts enter the repository from an offline signing host; the server holds only the public-key trust root, and terminals accept only desired states that pass verification.

  1. 01

    The master key stays offline

    The master key lives on media that never touches a network and is used only to issue subkeys and licenses. It never enters the server, and never enters CI.

  2. 02

    Subkeys sign artifacts

    Builds run on an offline host or in CI, and the signing subkey issues detached signatures over artifacts. The server does no online builds and no binary patching — that would break the signing chain.

  3. 03

    The server holds only public keys

    The server imports the public key as its trust root and owns the repository, BOM desired states, job orchestration, seat licensing, and the operation log. Private-key exposure shrinks to a single signing host.

  4. 04

    enforce on both gates

    Ingest and delivery both verify signatures. Production must use enforce; dev is only for local integration testing. Delivery also passes the license and terminal authorization gates.

  5. 05

    Constrained execution on terminals

    The agent runs as root, but actions are bound three ways by the systemd unit allowlist, ALLOW_POWER / ALLOW_LOCAL, and the node key. Playback protection is enforced on both the server and the terminal.

05 · DEPLOY

One command to install, one command to join

The server ships as a Linux multi-arch management build, Linux amd64 / arm64 audio builds, and a Windows amd64 build. Linux terminal installers detect amd64 / arm64 / armhf and pull the matching deb from the server's /dl/; management builds contain no ALSA playback, so choose the audio build for real playback. The Android terminal joins the network once you install the APK and enter the server address and token.

A

Server · Linux multi-arch management build

systemd
sudo apt-get update && sudo apt-get install -y gnupg
tar -xzf Zephyr-HiFi-Kit-server-0.54.tar.gz
cd Zephyr-HiFi-Kit-server-0.54/server
sudo ./install.sh
curl -s http://127.0.0.1:8080/api/v1/health

The installer lays down the binary, the systemd unit, configuration, the public-key trust root, and the /dl distribution directory. Complete first-time admin setup by opening http://localhost:8080/ on the server itself, or by reaching the server's localhost through an SSH tunnel. Secure remote deployment requires direct HTTPS with real TLS; terminating TLS at a reverse proxy does not satisfy the current admin-operation gate.

B

Terminals · one command each

Arch auto-detect

After initialization, sign in to the console and open Terminal Center → Add terminal. The wizard generates a one-time token and an install command; run it on the target terminal. No admin credentials are needed for this example.

curl -fsSL http://<server-IP>:8080/dl/agent-install.sh | \
  sudo bash -s -- --server http://<server-IP>:8080 \
                  --token <one-time-token>

After the Terminal Center → Add terminal wizard issues a token, it prints the same command. On an offline network you can install the bundled deb directly with dpkg -i. A terminal that registers appears in the console immediately.

Server · Windows amd64

PowerShell
Expand-Archive -Path .\Zephyr-HiFi-Kit-server-0.54-windows-amd64.zip -DestinationPath .
Set-Location .\Zephyr-HiFi-Kit-server-0.54-windows-amd64

The unzipped ZIP root is Zephyr-HiFi-Kit-server-0.54-windows-amd64/, with the EXE, start.ps1, and dist/ all at the root — do not descend into server/. start.ps1 listens only on HTTP 127.0.0.1:8080 by default, with ZAT on 0.0.0.0:7800. Set the admin account and sign in first at http://localhost:8080/ on the same machine.

To allow LAN access, set $env:HIFIHUB_LISTEN='0.0.0.0:8080' before starting and configure the firewall as needed, opening only the ports trusted terminals require. Admin setup and admin operations still have to come from the machine's own localhost or over direct HTTPS; do not work around authentication by widening the listener or forging proxy headers. Never expose passwords, one-time tokens, or node keys. For remote administration, use an SSH tunnel to the server's localhost.

Windows is tested locally; v0.54 release and artifact availability are subject to the automated verification result. The Windows pure-Go server currently decodes supported integer-PCM WAV and does not automatically invoke ffmpeg to decode FLAC; convert to WAV copies yourself, or use the Linux libFLAC audio build. External tools are not bundled, and actual output still needs an audio or Android terminal.

07 · FAQ

Frequently asked questions

Does the server need internet access?

No. Master key operations and license issuance can run fully offline. The server only verifies signatures at ingest and pushes artifacts to terminals at delivery, so the whole chain can run inside an isolated LAN. Terminal installers fetch packages from the server's /dl/ and never reach the public internet.

Why no online builds or binary patches?

Online builds would require the server to carry a cross toolchain for every application, which is unacceptable in size and attack surface; binary patches would break the signature chain of signed artifacts. Both were removed in favor of one verifiable path: offline/CI build → sign → upload to the repository.

Will upgrades interrupt a terminal that is playing?

No. Playback gating (FR-3.10) runs on both the server and the terminal: jobs enter waiting_idle until the terminal is free, and system upgrades, service stops, and shutdown are blocked during playback as well. The server returns 409, and the terminal's local console refuses as well.

How does licensing work?

The server ships with authorization for 3 terminals. Beyond that, a private issuer can sign expansion licenses offline; the server verifies them with the issuer's public key and tracks seat usage. Terminals need no certificate.

How do staged rollouts advance?

Ring percentages must sum to 100, and the bound BOM version must already be published. While the current ring still has unfinished jobs, advancing one step returns 409 so a failure does not spread to the next ring. Deleting a rollout does not revoke jobs already delivered, and the change can be undone.

Where does console authentication happen?

The console has built-in single-admin authentication, and first run walks you through setting the admin name and password. Admin operations are allowed only from the server's own localhost or over direct HTTPS; the backend does not trust TLS forwarding headers from reverse proxies.

What if I delete a BOM version or a terminal by mistake?

BOM keeps full version history and can roll back to any published version; a rollback creates a new published version instead of overwriting history. Deregistered terminals can be restored. Destructive actions in the console all come with an undo entry.

Which terminal hardware is supported?

The installer detects amd64, arm64, and armhf automatically, covering x86 mini PCs, Raspberry Pi 4/5 (64-bit), and Raspberry Pi 2/3 (32-bit). The management agent depends only on the standard library, and debs are produced by the built-in debpack, so target machines need no build tools.

Is the audio playback real? How do the management and audio builds differ?

Yes. The management build is pure Go (CGO_ENABLED=0) with placeholder ALSA output, suited to orchestration-only setups without audio hardware; the audio build decodes with CGO + libFLAC and outputs bit-perfect ALSA on the terminal, streamed over the ZAT protocol. Audio-build verification covers amd64 / arm64 builds, an ALSA null loopback, and a FLAC decode round trip (asserting bit-identical PCM); v0.54 results are subject to the release's automated verification record. Both builds share the same engine name, configuration, and systemd unit, so they are interchangeable.

How are music libraries connected, and which formats are supported?

The Linux server mounts SMB/CIFS shares with the kernel's mount.cifs (requires cifs-utils), scans the library, identifies formats by file header (WAV / FLAC and others), and ingests them as playable tracks. During playback the server decodes and streams over ZAT to authorized terminals, which output through ALSA. Mount credentials are written to a restricted file and never appear on the command line or in API responses.
